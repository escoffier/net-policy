# net-policy: Phase 6a — iptables Rules + Legacy Control Protocol Retirement Design

## Overview

Phase 6 of the C++→Rust migration (see the [overall roadmap](2026-07-29-cpp-to-rust-migration-design.md)) was originally described as "NFQ/netlink core... `net-policy.cpp`/`.h` main loop, `NFQ_RES_INFO`, epoll wiring, `admin/profile.cc` (netns), vendored `libmnl`/`libnetfilter_queue`/`libnetfilter_conntrack`/`libnfnetlink`... replaces the vendored C netlink libs entirely... highest risk and effort; done last." Reading the actual code shows this description needs two corrections and, given the genuinely heterogeneous risk profile of what it bundles, a size correction too:

- `admin/profile.cc` is **gperftools heap profiling** (`Heap::startProfiler`/`stopProfiler`/`handleHeapProfile`), not network-namespace code. The real netns-switching code (`OpenLocalNetNs`/`SetLocalNetNs`/`SetNs`, built on `open()`/`unshare(CLONE_NEWNET)`/`setns()`) lives directly in `net-policy.cpp`.
- The legacy raw-socket JSON control protocol (port 9999, `NetDataType` enum) that the [Phase 2 design spec](2026-07-31-cpp-to-rust-phase2-grpc-control-service-design.md) intended to retire ("gRPC becomes the only control plane") is **still fully wired up and listening** — `RunNetPolicyDaemon` still binds/listens/epoll-registers it, and `ParseRcvData`'s dispatch switch still handles all 11 real `NetDataType` message types. Checking `grpc/control_dispatch.h` shows every one of those 11 types (`kPodPid`→`GrpcDispatchPodUp`, `kPodDie`→`GrpcDispatchPodDown`, `kAddRule`→`GrpcDispatchAddPolicyRule`, `kDelRule`→`GrpcDispatchDeletePolicyRule`, `kAddWafRule`→`GrpcDispatchAddWafRule`, `kDelWafRule`→`GrpcDispatchDeleteWafRule`, `kHeapDump`→`GrpcDispatchDumpHeapProfile`, `kConfDump`→`GrpcDispatchDumpConfig`, `kConnDump`→`GrpcDispatchDumpConnections`, `kReset`→`GrpcDispatchResetConfig`, `kNodeCfg`→`GrpcDispatchUpdateNodeConfig`, `kLogLevel`→`GrpcDispatchSetLogLevel`) already has a working gRPC dispatch equivalent, live-tested by `net_rule_grpc_test`'s `GrpcRustControlEndToEndTest` suite. The legacy protocol is confirmed dead in spirit, just never actually deleted.
- The genuine scope Phase 6 bundles — NFQ packet-queue netlink, conntrack netlink, the epoll main loop, `NFQ_RES_INFO` lifecycle, netns switching, iptables rule management, and this legacy protocol — spans wildly different risk levels: the pure-Rust `nfq` crate (nbdd0121/nfq-rs, MIT/Apache-2.0, talks to the kernel via raw netlink sockets, `set_verdict`/`Message` API) looks reasonably capable for the NFQ piece, while the existing pure-Rust conntrack crate reportedly only implements `Dump()` — not the event-subscription callback (`nfct_callback_register(..., NFCT_T_ALL, UpdateNetSession, ...)`) this codebase actually needs. Bundling all of this into one monolithic phase would mean the hardest, least-certain piece (conntrack) gates everything else. Phase 6 is therefore split into three sub-phases, each independently planned, executed, and reviewed:
  - **Phase 6a (this spec):** iptables rule management (Rust) + legacy control protocol retirement (deletion). Fully self-contained, no netlink dependency, no coupling to NFQ/epoll/netns.
  - **Phase 6b (planned separately, when it starts):** the NFQ packet-queue netlink layer, the epoll main loop, `NFQ_RES_INFO` lifecycle, and netns switching (`SetNs`/`OpenLocalNetNs`/`SetLocalNetNs`) — bundled together because netns switching is called from directly inside the same sequential per-pod setup/teardown operations this sub-phase migrates (`SetNs`→`InitNfqueue`→`WriteIptableRule` at setup; `SetNs`→`ClearIptabelsRule`→`FreeResource` at teardown — see rule-detail.cpp:342-350), not a cleanly separable piece.
  - **Phase 6c (planned separately, when it starts):** conntrack, using an FFI-wrap-the-existing-C-library approach (Rust owns the lifecycle/state-machine and call sequencing; `cxx` FFI calls into the still-vendored `libnetfilter_conntrack` for the actual netlink protocol work) rather than a full pure-Rust netlink reimplementation, given the immaturity of the current Rust conntrack-event-subscription ecosystem. Full deletion of the vendored C library is a later follow-up, contingent on that ecosystem maturing.
  - **Heap profiling** (`admin/profile.cc`, gperftools) is explicitly deferred past all of Phase 6 to the Decommission phase (Phase 7 in the original roadmap) — the original roadmap's own cross-cutting-concerns section ties its Rust replacement to "when the last C++ binary using them goes away," which isn't true yet after 6a, 6b, or 6c individually (the daemon remains substantially C++ — HTTP codecs, WAF plugin orchestration, `main.cpp` — regardless of this phase's outcome).

## Goals (Phase 6a only)

- Move `WriteIptableRule`, `ClearIptabelsRule`, `CheckIptablesRule`, `GetIptablesVersion` (all pure `system()`/`popen()` shell-outs to the `iptables`/`iptables-legacy` CLI — no netlink, no epoll, no NFQ coupling) to a new Rust crate.
- Delete the legacy raw-socket JSON control protocol: the port-9999 socket bootstrap in `RunNetPolicyDaemon`, `CtrlServer` (class, `ctrl_server_` member, `CtrlSrv()` accessor), `ProcAcceptEvent`, `ParseRcvData`, `ParseRcvJson`, `ReadData`, and the `NetDataType`/`NET_DATA_TYPE` enum (confirmed used nowhere outside this dispatch chain).
- Preserve every real call site of the surviving functions: `WriteIptableRule` (called from `GrpcDispatchPodUp`, `net-policy.cpp:1978`, once its other call site inside the deleted `ParseRcvData` disappears) and `ClearIptabelsRule` (called from `PolicyRule::ClearCfg`, `rule-detail.cpp:348`) keep working identically, just backed by Rust.

## Non-Goals (deferred to later sub-phases)

- **NFQ packet-queue netlink** (`OpenNfque`, `input_nfq_cb`/`output_nfq_cb`, `NfqueueRcvData`) — Phase 6b.
- **Netns switching** (`OpenLocalNetNs`/`SetLocalNetNs`/`SetNs`) — Phase 6b, per the coupling reasoning in Overview. Stays exactly as-is in this sub-phase; `net-policy.cpp`'s `SetNs` call sites (both the one this phase deletes inside `ParseRcvData`'s `kPodPid` case, and the one inside `GrpcDispatchPodUp`, and the one inside `PolicyRule::ClearCfg`) are unaffected — none of them are touched by 6a.
- **The epoll main loop and `NFQ_RES_INFO` lifecycle** (`RunNetPolicyDaemon`'s `while(1)` loop, `AddEpollEvent`, `InitNfqueue`, `NFQ_RES_INFO` itself) — Phase 6b. This sub-phase's deletion of the legacy socket's bootstrap code touches `RunNetPolicyDaemon`, but only the lines specific to the `zListenFd`/`unixEvent` setup — the epoll loop itself, the Rust gRPC control/event server bootstrap, and the `PostServer`/post-notification socket (port 8888, unrelated — used for WAF/match-event pushes to pods, not control-plane RPCs) are untouched.
- **Conntrack** (`OpenConntrack`, `UpdateNetSession`) — Phase 6c.
- **Heap profiling** (`admin/profile.{h,cc}`) — deferred to the Decommission phase, per Overview.
- **`ParseNetPolicy`, `ParseNodeCfg`, `DeletePolicy` (free function), `AddNewHttpPolicy`, `AddNewPolicy`, `UpdateMark`, `dumpConnectons`** — these are NOT part of the legacy protocol being deleted. They're shared: the gRPC dispatch functions (e.g. `GrpcDispatchAddPolicyRule`, confirmed at `net-policy.cpp:2261-2270`) build a JSON string from protobuf-sourced fields and call these exact same functions — an intentional "translate proto → JSON, reuse the existing JSON-driven mutation logic" bridge from Phase 2. They stay untouched; only the legacy protocol's *outer dispatch shell* (`ParseRcvData`'s switch, `ParseRcvJson`'s envelope parsing, the socket/epoll bootstrap) is deleted.
- **`NetCtrlInfo`/`NET_CTRL_INFO`** (the struct, not the `NetDataType` enum) stays — it's `InitNfqueue`'s parameter type and is constructed (with just `pid_`/`pod_id_` populated) inside `GrpcDispatchPodUp` too (`net-policy.cpp:1971`). Only `NetDataType`/`NET_DATA_TYPE` (the enum) and the one field that carries it (`ctrl.msg_type_`, used only inside the deleted dispatch chain) go away.

## Architecture

**iptables crate.** A new Rust crate (e.g. `net_iptables`, following the `staticlib`/`cxx`-bridge/Corrosion pattern every prior phase used) exposes four free functions mirroring the C++ originals' signatures exactly: `write_iptable_rule(i_mark: i32, o_mark: i32, ipt_ver: i32, waf_enable: bool)`, `clear_iptables_rule(ipt_ver: i32)`, `check_iptables_rule(ipt_ver: i32) -> bool`, `get_iptables_version() -> i32`. No opaque type, no per-instance state — these are pure, stateless shell-out wrappers (mirroring the C++ originals, which are free functions with no persistent state of their own), so the `cxx` bridge is the simplest possible shape: plain functions, scalar arguments, scalar/bool returns. `std::process::Command` replaces `system()`/`popen()`; `Command::output()`'s captured stdout replaces `popen()` + `fread()` into a fixed buffer (an improvement — `popen()`'s `fread(buf, 1, sizeof(buf), fp)` into a 1024-byte stack buffer silently truncates any `iptables -S` output longer than 1024 bytes, though in practice the greppable line being searched for is short and appears near the start of output; note this as a behavior-preserving-in-practice, defensively-improved-in-theory port, not a deliberate deviation requiring a differential test — there's no plausible input where the old and new code would produce different pass/fail results for the substring checks these functions do).

**No differential test needed for this sub-phase.** Every prior phase's differential-testing rationale (Phase 4's policy matching, Phase 5's TCP/IP parsing) applied to pure, deterministic, no-I/O logic where subtle semantic mismatches were a real risk. This sub-phase's logic is "build a command string, shell out, grep the output for a substring" — trivially portable with no interesting edge cases to lose in translation, and the actual `iptables` binary being invoked is the same regardless of which language issues the `Command`/`system()` call. Ordinary integration tests (real `iptables` invocations against a scratch namespace, or — more practically, given this runs inside the project's Docker build container — assertions against captured `Command` output for known-shape `iptables -S` output) are sufficient.

**Legacy protocol deletion is a pure C++ removal — no Rust component.** This is the same shape as Phase 4/5's Task-1-style dead-code deletions (`policy/engine.{h,cc}`, `net/filter.{h,cc}`, `net/udp.{h,cc}`): confirm zero external references, delete, verify build+tests still pass. The one nuance here versus those prior deletions: this dead code is a live, listening, reachable network socket in production (port 9999) that just happens to have no client base migrated onto it (or a client base already fully migrated onto the gRPC control plane, per Phase 2's stated intent — this spec doesn't have visibility into which, and doesn't need to: what matters is that every message type it can dispatch is already reachable via a working gRPC RPC, so removing it removes redundant capacity, not capability).

## Testing & Rollout

- **iptables crate:** Rust unit tests verify the four functions build the exact command strings the C++ originals built (string-comparison tests against a fake/injectable command runner, or — simpler, given these are thin wrappers around real system calls with no meaningful internal logic to unit-test in isolation — integration-style tests that actually invoke `iptables` inside the build container and assert on real before/after `iptables -S` state, mirroring what a human would do to manually verify the C++ version). Existing C++ integration coverage (if any exercises `WriteIptableRule`/`ClearIptabelsRule` today) continues to apply unchanged, since the call sites and their contracts don't change.
- **Legacy protocol deletion:** verify via `grep` (per every prior phase's Task 1 pattern) that `CtrlServer`, `ProcAcceptEvent`, `ParseRcvData`, `ParseRcvJson`, `ReadData`, and `NetDataType`/`NET_DATA_TYPE` have zero references outside the code being deleted, then delete and confirm `net_rule_test`/`net_rule_grpc_test` still pass in full (they should be entirely unaffected — no test in either suite exercises the port-9999 socket path; the gRPC-side `GrpcRustControlEndToEndTest` suite is what actually covers the surviving control-plane behavior).
- This is a **direct cutover** for both pieces, not a shadow-run — the iptables port has no interesting behavior-preservation risk to shadow-run against (see Architecture), and the legacy protocol is being deleted, not replaced, so there's nothing to run in parallel.

## Final State

A new Rust crate owns iptables rule management (`write_iptable_rule`/`clear_iptables_rule`/`check_iptables_rule`/`get_iptables_version`), called from the same two C++ call sites (`GrpcDispatchPodUp`, `PolicyRule::ClearCfg`) as before. The legacy raw-socket JSON control protocol (port 9999) — `CtrlServer`, `ProcAcceptEvent`, `ParseRcvData`, `ParseRcvJson`, `ReadData`, `NetDataType`/`NET_DATA_TYPE` — no longer exists; the gRPC control plane (port 50051, from Phase 2) is the sole control-plane entry point, finally realizing Phase 2's original stated intent. `net-policy.cpp`'s `RunNetPolicyDaemon` main loop, `NFQ_RES_INFO`, NFQ/conntrack netlink code, and netns switching are all unchanged, awaiting Phase 6b/6c.
