# net-policy: Phase 6b-1 — Unified Packet Parsing and Connection Decision Design

## Overview

Phase 6 of the C++→Rust migration (see the [overall roadmap](2026-07-29-cpp-to-rust-migration-design.md)) was split into 6a (iptables + legacy protocol retirement, shipped), 6b (NFQ/epoll/netns), and 6c (conntrack), per [Phase 6a's design spec](2026-08-03-cpp-to-rust-phase6a-iptables-legacy-retirement-design.md). Reading the actual NFQ packet-processing code (`input_nfq_cb`/`output_nfq_cb` in `net-policy.cpp`) shows Phase 6b itself needs a further split: these callbacks aren't a thin netlink wrapper around business logic that lives elsewhere — they combine three genuinely separable concerns that were never disentangled:

1. **NFQ netlink protocol mechanics** — `nfq_open`/`bind`/`create_queue`/`set_mode`, reading raw netlink messages, issuing verdicts. Genuinely portable to Rust independent of everything else.
2. **A duplicated, redundant packet-parsing and TCP-tracking problem.** Phase 5 built `net_flow_engine` (Rust) for `net::ConnectionManager`, but `ConnectionManager::receive` is only called when `WafEnabled()` — a separate, independent, hand-rolled parser (`parse_package`, a third five-tuple extractor alongside Phase 5's and the one this document's Task 1 further extends) and TCP tracker (`MicroSegEngine::TcpCtInput()`/`TcpCtOutput()`, a raw `std::map<TcpFourTupleV4, http::ConnectionPtr>`) runs **unconditionally**, for every packet, to drive microsegmentation's own HTTP-rule matching (`InputHttpPolicy()`/`OutputHttpPolicy()`). When WAF is enabled, the same packet bytes get parsed and TCP-tracked twice, by two independent state machines that have never been aware of each other.
3. **The actual enforcement dispatch logic** — L3-L4 policy matching (`MatchNetPolicyRule`/`MatchMicroPolicyRule`, already Rust-delegated via Phase 4's `policy_engine`), L7 HTTP rule matching for microsegmentation, WAF dispatch, post-match event notification (`PostServer::SendMatchMsg`), and a conntrack-mark fast-path (`SetAcceptMark`) that lets already-decided flows bypass NFQUEUE entirely via the iptables rules Phase 6a wrote.

Given this, Phase 6b is split into three ordered sub-phases:
- **Phase 6b-1 (this spec):** make `net_flow_engine`/`net::ConnectionManager` the single, canonical packet-parsing and TCB-decision service for the *whole* daemon — both WAF and (in 6b-2) microsegmentation — eliminating the double-parse. Pure C++/Rust restructuring; the NFQ/epoll invocation machinery around the callbacks is untouched.
- **Phase 6b-2 (planned separately, when it starts):** migrate microsegmentation's `TcpCtInput`/`TcpCtOutput` onto the shared decision this phase establishes, deleting the redundant hand-rolled tracker.
- **Phase 6b-3 (planned separately, when it starts):** port the NFQ netlink mechanics themselves to Rust (`nfq_open`/`bind`/`create_queue`/`set_mode`, verdict issuance), plus `NFQ_RES_INFO` lifecycle and netns switching. By this point the callback bodies are already consolidated and simplified, so this becomes a cleaner "Rust owns protocol mechanics, C++ orchestrates" swap, matching Phase 5's pattern.

This spec also flags two findings from reading the current code that don't block Phase 6b-1 but are worth recording:
- **`SetLocalNetNs` (the function that would switch the daemon back to its own host namespace after entering a pod's) has zero callers anywhere**, and `DaemonContext::LocalNetNsFd()` — the fd it would need — is captured at startup (`OpenLocalNetNs()`) but never read by anything. The daemon appears to never return to its own namespace once it first enters a pod's, apparently by design (every socket needing the host namespace — the gRPC servers, `PostServer` — is created before the first `SetNs()` call at pod-lifecycle time), but this is genuinely confirmed-dead machinery, not something Phase 6b-1 needs to touch. Scoped to Phase 6b-3 (which owns netns switching) to either delete or explain.
- **`NfQueData::ClearNfQueResource`** (flagged during Phase 6a's review) still has zero callers anywhere in the codebase — neither `GrpcDispatchResetConfig` (calls `Microseg().ClearCfg()`, which only touches the Rust policy engine) nor `GrpcDispatchPodDown` (calls `DeleteNfQueRes`, a different method) reach it. Also scoped to Phase 6b-3, which owns `NFQ_RES_INFO` lifecycle wiring.

## Goals

- Extend `net_flow_engine`'s `FlowEngine`/`PacketDecision` to parse **all** protocols relevant to policy matching (TCP, UDP, ICMP) — not just TCP. Today, `on_packet_internal` returns `None` outright for anything that isn't `IPPROTO_TCP` (`crates/net_flow_engine/src/lib.rs:290`), because Phase 5 built it purely for TCB tracking, which only exists for TCP. Policy matching (`MatchNetPolicyRule`) needs a five-tuple for every protocol `parse_package` currently handles (TCP/UDP/ICMP), so `FlowEngine` needs a new decision path that reports the parsed five-tuple for non-TCP protocols too (no TCB tracking involved, since UDP/ICMP have no connection state to track — this is pure header parsing, the same shape as Phase 5's already-shipped `parse_ipv4_header`).
- Redesign `net::ConnectionManager::receive`'s contract: instead of internally driving WAF-specific dispatch (`HandleNewConnection`/`HandleData`/`HandleClosed`, hardwired to `filter_factory_`/`http_conns_`), it returns the parsed five-tuple and TCB decision to its caller. The caller (currently `input_nfq_cb`/`output_nfq_cb`) becomes the orchestrator, calling `ConnMgr().receive(pkg, len)` exactly once per packet and using the result for both L3-L4 policy matching (replacing `parse_package`) and — unchanged in behavior, just relocated — WAF dispatch.
- Relocate the WAF-dispatch logic currently inside `ConnectionManager::Handle{NewConnection,Data,Closed}` to the call site, byte-for-byte behaviorally identical, just moved to a location the caller can invoke conditionally (only `if (daemon->WafEnabled())`, matching today's gating).
- Zero behavior change for WAF traffic, verified against Phase 5's existing test suite (`ConnectionManagerCutoverTest` and friends) plus new caller-side tests covering the relocated dispatch.

## Non-Goals (deferred to later sub-phases)

- **Migrating `TcpCtInput`/`TcpCtOutput` and microsegmentation's HTTP tracking onto the shared decision** — Phase 6b-2. This spec's `ConnectionManager` redesign makes that migration possible (the decision is now available to any caller, not just WAF), but doesn't perform it. `input_nfq_cb`/`output_nfq_cb` still call their own `parse_package`+`TcpCtInput`/`TcpCtOutput` logic for the microseg path after this phase — only the *policy-matching* five-tuple source changes (from `parse_package` to `ConnectionManager`'s decision), not microseg's TCP-tracking source.
- **NFQ netlink mechanics, `NFQ_RES_INFO` lifecycle, netns switching** — Phase 6b-3.
- **Conntrack** (`OpenConntrack`, `UpdateNetSession`, `SetAcceptMark`) — Phase 6c.
- **`SetAcceptMark`'s conntrack-mark fast-path itself** — unchanged; it consumes the policy-match verdict, which this phase doesn't alter, only relocates where the five-tuple driving that verdict comes from.
- **`PostServer::SendMatchMsg`, `MatchHttpPolicyRule`, `MatchMicroPolicyRule`'s reverse-match logic** — unchanged business logic; this phase only changes where the `FiveTuple` these functions consume is parsed from.

## Architecture

**Extending `FlowEngine` for non-TCP five-tuples.** `parse_ipv4_header` (Phase 5, unchanged) already extracts `protocol`/`saddr`/`daddr`/`header_len` for any IP packet. What's missing is UDP/ICMP port extraction. UDP's header is trivial (8 bytes: source port, dest port, length, checksum — the same shape `net/udp.cc`'s now-deleted `Udp::receive` used to read before Phase 5 confirmed it dead). ICMP has no ports at all — `parse_package`'s existing handling (`src_port = 0; dst_port = 0;`) is the precedent to replicate exactly, not reinvent. Add a new internal decision path — not a new `PacketKind` variant reusing the TCB-lifecycle vocabulary (`NewConnection`/`Data`/`Closed` are meaningless for UDP/ICMP), but a parallel, simpler decision the FFI layer exposes alongside `on_packet`: a `parse_five_tuple`-shaped function that returns `{proto, saddr, daddr, sport, dport}` for TCP, UDP, or ICMP, doing no TCB bookkeeping — a pure, stateless parse (`&self`, not `&mut self`), independent of `on_packet`'s connection-tracking side effects. `on_packet` (TCB tracking, TCP-only, unchanged) and this new five-tuple parse are two different entry points into the same crate, not one call serving two purposes — a TCP packet's caller will call both (once for the five-tuple, once for the TCB decision) since policy matching and connection tracking are genuinely different concerns even when Phase 6b-2 later unifies where they're both driven from.

**`ConnectionManager`'s new contract.** `receive` changes from `NetStatus receive(const uint8_t*, size_t)` to something that returns both a five-tuple (for the caller's policy-matching use) and enough of the `PacketDecision` for the caller to drive WAF dispatch itself. Concretely:
```cpp
struct ReceiveResult {
  FiveTuple tuple;         // populated for every recognized protocol (TCP/UDP/ICMP)
  net_flow::PacketDecision decision;  // TCB decision; only meaningful for TCP (kind != Ignore)
  bool is_tcp;
};
ReceiveResult ConnectionManager::receive(const uint8_t* pkg, size_t len);
```
`Handle{NewConnection,Data,Closed}` move out of `ConnectionManager` verbatim (same bodies, same `http_conns_`/`filter_factory_` state — `ConnectionManager` keeps owning those, since WAF dispatch is still logically "the thing `ConnectionManager` does with a TCP decision," just invoked by the caller instead of internally) into public methods the caller invokes explicitly: `manager.DispatchWaf(result.decision, pkg, len)`. This keeps the change mechanical and low-risk — the WAF-dispatch *code* doesn't move to a different file or get rewritten, only the *call site* moves from inside `receive` to the caller, gated by the same `if (daemon->WafEnabled())` check `input_nfq_cb` already has today.

**Caller-side orchestration (`input_nfq_cb`/`output_nfq_cb`).** Confirmed current order (`net-policy.cpp:637-650`): `parse_package(pkg, tuple, &tcphdr, offset)` runs first and unconditionally; only afterward, gated on `daemon->WafEnabled() && tuple.proto_ == IPPROTO_TCP`, does `daemon->ConnMgr().receive(...)` run. After this phase, that inverts: `ConnMgr().receive(pkg, data_len)` runs first and unconditionally (replacing the `parse_package` call entirely, not just reordering around it); its returned `tuple` feeds `MatchNetPolicyRule`/`MatchMicroPolicyRule` for every protocol; its returned `decision` feeds `WafEnabled() ? DispatchWaf(...) : (nothing)` for TCP only — UDP/ICMP packets get a `ReceiveResult` with `is_tcp = false` and no meaningful `decision`, so WAF dispatch is skipped for them exactly as today (`tuple.proto_ == IPPROTO_TCP` is already a precondition for entering the WAF branch in the current code).

**A pre-existing quirk in `parse_package`'s caller, to preserve or deliberately fix — not silently change either way.** `net-policy.cpp:638-639`: `if (ret != kNfMatchRule) nfq_set_verdict(qh, id, ret, 0, NULL);` has no `return` after it — if `parse_package` fails (unrecognized IP version or protocol), a verdict is issued but `input_nfq_cb` keeps executing, continuing to use a `tuple` whose `proto_`/port fields were never set for that failure path (only `src_addr_`/`dst_addr_` are populated before `parse_package`'s internal protocol `switch`). Whether this causes a second, harmless-or-not `nfq_set_verdict`/`verdict2` call later in the same invocation for the same packet ID isn't verified here. Since this phase removes the `parse_package` call this bug lives in, replicating it exactly means `ConnectionManager::receive`'s equivalent "unrecognized protocol" path must ALSO fall through rather than return early with an obvious guard — Task 4 (below) must read this exact control flow against current source, decide whether to replicate the fall-through bug-for-bug or fix it with an early `return`, and document the choice explicitly in its commit message, per this project's established practice for flagged-not-silently-resolved quirks (e.g. Phase 4's `mask == 0` CIDR case, Phase 5's IPv4-header-length bounds check).

**Why not fold WAF dispatch permanently back into `ConnectionManager::receive`, just extended to also return the tuple?** Because Phase 6b-2 needs the *same* decision available to drive microsegmentation's downstream too, and `ConnectionManager` owning "decide, then unconditionally drive WAF" would force microsegmentation's dispatch to be bolted onto the same method (via a flag, a callback, or a second owned-map) — reintroducing the kind of hidden coupling this phase exists to remove. Returning the decision and letting the caller decide what to do with it is the same seam shape Phase 4/5 already established elsewhere (`MatchFiveTuple`, `FlowEngine::on_packet` — Rust/decision-layer code returns a verdict, C++ orchestrates side effects), applied one layer up.

## Testing & Rollout

- **`FlowEngine`'s five-tuple extension**: ordinary Rust unit tests (UDP header parsing, ICMP zero-port handling, protocol dispatch) — this is deterministic, no-I/O, pure parsing, the same testing shape Phase 5 used for `parse_ipv4_header`/`parse_tcp_header`. No differential test needed for the parsing itself (same reasoning as Phase 5: nothing quirky or legacy-behavior-dependent to replicate bug-for-bug in a fresh UDP/ICMP parser that never existed in Rust before).
- **`ConnectionManager`'s contract change**: this is the risky part — it changes the call boundary of already-shipped, production WAF-dispatch code. Verification:
  1. Every existing WAF-path test (`ConnectionManagerCutoverTest.HandleDataPassesTcpHeaderStartNotIpHeaderStartToFilters`, `HandleClosedInvokesOnCloseAndRemovesBothConnections`, and the broader `net_rule_grpc_test`/`net_rule_test` suites) must pass unmodified in structure — only the call sites they exercise change shape (`manager.receive(...)` returning a `ReceiveResult` instead of driving dispatch itself, followed by an explicit `manager.DispatchWaf(...)` call), not the assertions about *what* WAF observes.
  2. A new caller-orchestration test exercising the full path this phase changes: build a `ConnectionManager`, call `receive` for a SYN/data/FIN sequence, confirm the returned `ReceiveResult.tuple` matches what `parse_package` would have extracted for the same bytes, then confirm calling `DispatchWaf` on the returned decision produces the identical `HttpFilterManager` observations the old internal-dispatch path produced (reuse `ConnectionManagerCutoverTest`'s `CapturingFilter` infrastructure).
  3. A UDP and an ICMP synthetic-packet test confirming `receive` returns a populated `tuple` with `is_tcp = false` and no WAF dispatch is attempted (this is new behavior — today, `parse_package` alone handles non-TCP five-tuples and `ConnectionManager` is never even called for them).
- **Direct cutover**, not a shadow-run — same rationale as every prior phase on this hot path: this sits directly in live packet-forwarding, a pure/deterministic decision layer is the right verification tool (test it exhaustively before flipping, not run two paths in parallel in production), and Phase 5's existing test suite is the regression safety net for "did WAF behavior actually stay identical."

## Final State

`net_flow_engine` parses five-tuples for TCP, UDP, and ICMP (previously TCP-only), alongside its existing TCP-only TCB-tracking `on_packet`. `net::ConnectionManager::receive` returns a `ReceiveResult` (five-tuple + TCB decision) instead of internally driving WAF dispatch; `DispatchWaf` (same logic Phase 5 wrote, relocated) is a separate method callers invoke explicitly. `input_nfq_cb`/`output_nfq_cb` call `ConnMgr().receive` once per packet, unconditionally, and use its result for both policy-matching (replacing `parse_package`) and — gated on `WafEnabled()` and TCP, exactly as today — WAF dispatch. Microsegmentation's own `TcpCtInput`/`TcpCtOutput` tracking is untouched (Phase 6b-2). NFQ netlink mechanics, `NFQ_RES_INFO`, netns switching, and conntrack are untouched (Phase 6b-3/6c).
